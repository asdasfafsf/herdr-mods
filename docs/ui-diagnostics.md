# UI 오류를 나중에 확인하기

오류 화면이 다음 렌더에서 사라지면 `herdr-app status`에도 남아 있지 않을 수 있다. 화면 캡처를 사람이 매번 옮기지 않아도 오류 시각·스택·복구 여부를 확인하려고 `hm logs`를 둔다. `console.log`는 호스트 tracing으로 전달되지만 영속 파일은 보장되지 않는다. 진단기는 mod 밖의 Python 프로세스로 실행하여 mod 렌더가 중단돼도 계속 상태를 조회한다.

```sh
hm logs --watch     # 1초 간격 기록. 실행 중인 터미널에서 Ctrl-C로 종료
hm logs             # 다른 터미널에서 최근 50개 기록 확인
hm logs --json      # 같은 기록을 JSONL로 출력
hm logs --once      # 감시기가 없을 때 한 번 확인해서 저장
hm logs --stop      # 다른 터미널에서 감시 종료 요청(현재 조회 후, 최대 약 6초)
hm logs --render    # Agents Plus의 최근 렌더 시간 집계 (JSON은 --json 추가)
```

`./install.sh agents commands`로 설치한다. `agents-plus`가 화면에 없어도 설치된 진단기는 사용할 수 있다. 감시는 명시적으로 실행한 동안만 유지되며 자동 로그인 시작 서비스는 설치하지 않는다. 앱이 꺼지면 unavailable을 기록하고 다시 연결될 때까지 확인한다. 읽기 명령은 앱이 닫혀 있어도 된다.

파일은 `~/.config/herdr-app/diagnostics/ui.jsonl`, 별도 `HERDR_APP_HOME`을 쓰면 그 폴더의 `diagnostics/ui.jsonl`이다. 2MiB마다 회전하며 이전 파일 3개까지 남긴다. 동일 앱 홈에는 감시기 하나만 실행된다. `watch.lock`의 JSON에 있는 pid는 참고용이며 파일 존재만으로 실행 중이라고 판단하지 않는다. 종료 시 OS가 잠금을 해제한다. `--stop`은 해당 실행의 토큰으로 종료를 요청하며 PID만 보고 다른 프로세스를 종료하지 않는다.

| 기록 | 의미 |
|---|---|
| watch_started / watch_stopped | 감시 시작 / Ctrl-C 종료 |
| snapshot | 최초 정상 관찰 또는 연결 재개. error_count도 함께 확인 |
| errors | 최초 또는 변경된 오류. `errors` 문자열에 호스트가 반환한 오류·스택 |
| recovered | 이전 오류가 있었고 현재 조회의 errors가 비었음 |
| status_unavailable | 명령 실패·5초 초과·응답 형식 문제. 오류가 해결됐다는 뜻이 아님 |
| heartbeat | 같은 상태에서도 60초마다 감시가 살아 있음을 확인 |

시각은 UTC ISO 문자열이다. layout/현재 agent 식별자, 공유 파일 크기, 레포·checkout·agent_info 개수, 설치된 agents-plus/main.js SHA-256을 함께 남긴다. 대화·제목·실행 인자·shared.json 전체는 복사하지 않는다. 호스트의 오류 문자열 자체에는 파일 경로 등이 포함될 수 있다. 한 오류 목록은 32,000자로 제한하고 잘렸는지 표시한다.

## 확인 범위

### 렌더 시간 (`hm logs --render`)

Agents Plus 목록이 초기화되면 계측을 시작한다(정렬 메뉴 제외). 7개 구간의 `Date.now()` 차이를 메모리에 집계하고 60초마다 별도 Python 작업으로 `diagnostics/render.jsonl`에 저장한다. `--watch`와 독립적으로 동작하며, 렌더 안에서는 파일·프로세스·shared 쓰기나 추가 redraw를 하지 않는다. 이 파일도 2MiB + 이전 3개로 제한하고 여러 mod 사본의 쓰기를 잠금으로 직렬화한다.

- `completed`, `total_ms`, `max_ms`: 완료된 JS 요소 설명 생성 횟수·합계·최대. 평균은 `total_ms / completed`. 실제 GPU 프레임·호스트의 후속 요소 변환·레이아웃 시간은 포함하지 않는다.
- `phases`: `inputs`(호스트 초기 조회), `state`(부모 인덱스·Seen·ack), `ordering`(자손 긴급도·정렬), `labels`(pane·레포·이름), `groups`(섹션·표시 순서), `rows`(내부/외부 행), `container`(목록 컨테이너)의 합계·최대 ms. 구간별 최대는 서로 다른 렌더일 수 있어 합해서 전체 최대라 해석하면 안 된다.
- `slow`: 25ms 이상 완료 횟수. 이 값은 여유를 보기 위한 관찰 기준이며 호스트의 제한시간 설정이 아니다. `worst`는 가장 느린 완료 1건, `samples`는 느린 완료/미완료 최신 8건이다. 시각·구간 시간·개수·보기 모드만 담고 대화/이름은 넣지 않는다.
- `unfinished`: 시작했지만 종료 기록이 없는 렌더를 **같은 mod 인스턴스의 다음 렌더 또는 타이머가 발견한 횟수**. `last_phase`, `completed_phases`만 남기며 다음 실행까지의 대기 시간을 실행 시간으로 간주하지 않는다. 원인이 timeout인지 일반 예외인지 이 필드만으로 단정하지 않는다. 당시 외부 UI 오류 로그와 함께 읽는다.
- `invalid_clock`: 측정 중 시계가 뒤로 움직인 완료 표본 수. 시간 통계에서 제외한다. 밀리초 단위 벽시계라 짧은 구간은 0ms일 수 있고, 앞으로 시계가 조정되면 실제 실행보다 크게 보일 수 있다.
- `instance`로 mod 사본을 구분한다. `context`의 코드 해시와 규모는 **저장 시점** 값이다. 재시도 중 코드가 교체됐다면 측정 시점 코드와 같다고 단정하지 않는다.

저장 실패 시 한 묶음을 메모리에 유지하고 60초 뒤 재시도하며 console에 실패를 알린다. 최근 시각이 갱신되는지도 확인한다. **앱 종료·핫 리로드·VM 폐기로 아직 저장하지 못한 계측은 유실될 수 있다.** 중단 순간에도 반드시 파일에 남는 추적기는 아니다. 외부 `ui.jsonl` 수집기는 계속 따로 실행한다. 성능 로그는 측정에 쓰는 진단 자료이며 다른 앱으로 가져올 사용자 설정이 아니다.

느린 렌더를 수정하는 비교 방법과 완료 기록은 [렌더 성능 개선](render-performance.md)에 남긴다.

- 상태 조회 방식이므로 **조회 사이에 생겼다가 사라진 오류는 놓칠 수 있다**. host의 모든 예외를 직접 받는 기능은 아니다. 예전 오류도 소급 복원하지 않는다.
- `recovered`는 현재 오류 목록이 비었다는 뜻이다. 기능이 정상 동작하는지는 실제 화면·동작으로 별도 확인한다.
- `interrupted` 스택은 중단된 위치를 보여준다. 그 위치가 원인이라고 단정하지 않는다. 렌더 실행 제한·호스트 취소 등의 구분에는 호스트 로그/재현이 추가로 필요하다.
- 파일 기록 실패 시 감시기는 오류를 출력하고 종료한다. heartbeat의 최신 시각과 프로세스를 확인한다.

## 다른 앱으로 옮겼을 때 해결 조건

오류가 화면에서 사라진 뒤에도 발생·반복·회복을 구별하고 당시 코드와 데이터 규모를 확인할 수 있어야 한다. 같은 오류가 매초 파일을 채우면 안 되며, 앱 연결 실패를 회복으로 기록하면 안 된다. 새 앱이 영속 오류 스트림을 제공한다면 그것을 우선 사용하고 이 폴링을 대체한다.

## 복원 상태 (`hm logs --restore`)

`wt-restore`가 저장 실패(storage), 조회 실패(poll), 세션 ID 미식별(identity)과 회복을 `diagnostics/restore.jsonl`에 기록한다. `hm logs --restore --json`으로 최근 50개 원문을 읽는다. restore 번들과 commands만 있으면 되고 UI 감시 프로세스와 독립적이다.

동일 문제는 60초에 한 번, 상태 변화는 즉시 기록한다. 저장 중복은 파일 잠금으로 막고 최대 1MiB + 이전 파일 1개를 보존한다. 원인 문자열은 240자로 제한하며 제목·대화·argv는 넣지 않는다. 식별 실패에는 터미널 주소·agent 종류와 terminal_read_failed/foreground_unavailable/session_unresolved 단계만 남기므로 이름 중복/생략 중 무엇인지 확정하는 로그는 아니다. 저장 파일을 쓸 수 없어도 다른 경로의 진단은 남길 수 있지만 디스크 전체 장애에서는 둘 다 실패할 수 있다. 이때 알림과 console 경고가 보조 수단이다.

복원 파일 읽기 실패를 null로 바꿔 덮어쓰지 않고, 쓰기 실패 뒤에도 LIVE 매핑은 가능한 경우 갱신한다. 저장 캐시는 실제 쓰기 성공 뒤에만 전진하며 다음 5초 주기에서 다시 시도한다. 같은 인스턴스에서 복원 안내·자동 이어가기를 중복하지 않는다. 실제 코어 재시작 검증과 합성 실패 주입 검사는 별개다.
