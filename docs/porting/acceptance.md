# 이식 합격 사례

각 사례는 원래 불편이 해결됐는지 판단한다. 새 앱 기본 기능으로 충족해도 통과다. 아래 상태는 모두 **대상 앱 미실행**이며 이번 문서 작업에서 성공했다고 주장하지 않는다. 코드 정합성 검사와 UI 초기 렌더 검사는 이 전체 목록을 대신하지 못한다.

실행 기록에는 대상 앱/버전, 코드 revision, fixture, 실행 시각, 기대/실제 결과, 캡처 또는 로그, 통과/실패/제외 이유를 남긴다. 제거·복구·변환 시험은 복제한 테스트 레포와 분리한 에이전트 home에서 한다. 실제 작업을 죽여 시험하지 않는다.

기계가 읽는 원본은 [acceptance.json](acceptance.json), 기능 연결은 [catalog](catalog.md).

<a id="ac-p01"></a>
## AC-P01 · 폴더/레포 묶음 열기

- 준비: primary가 열린 app-a, 닫힌 app-b를 담은 부모 폴더
- 행동: UI Browse 후 Pick all; 별도로 CLI add 실행
- 기대 결과:
  - UI 초기 선택은 비어 있다
  - 이미 열린 app-a는 중복 생성하지 않는다
  - app-b를 연다
  - CLI는 미개방 레포를 모두 연다
- 상태: 대상 앱 미실행.

<a id="ac-p02"></a>
## AC-P02 · clone 후 작업 시작

- 준비: 존재하는 부모와 인증이 필요한 테스트 remote
- 행동: Clone 실행 후 같은 목적지로 다시 요청; 실패도 재현
- 기대 결과:
  - 인증 입력이 가능한 터미널이 열린다
  - 중복 요청은 거부한다
  - 성공 시 새 폴더의 셸이다
  - 실패 시 이유와 셸이 남는다
  - 요청 접수를 clone 완료로 보고하지 않는다
- 상태: 대상 앱 미실행.

## AC-W01 · 이름/base/PR 기반 worktree 생성

- 준비: origin/main, 기존 로컬/원격 브랜치, PR, 경로 충돌을 갖는 테스트 repo
- 행동: 새 이름/기존 브랜치/PR로 UI와 CLI 생성 비교
- 기대 결과:
  - 기본 base와 분기 우선순위가 behavior와 같다
  - 명시한 브랜치 편집을 유지한다
  - 경로 충돌은 번호를 붙인다
  - 잘못된 이름/미설치 agent는 명확한 오류다
  - UI와 CLI 결과가 같다
- 상태: 대상 앱 미실행.

<a id="ac-w04"></a>
## AC-W04 · checkout와 브랜치 안전 삭제

- 준비: dirty/working/blocked/merged/unmerged/기존 브랜치인 checkout 각각
- 행동: UI remove와 CLI rm; 승인된 경우에만 force
- 기대 결과:
  - primary는 거부한다
  - dirty/working/blocked는 기본 차단한다
  - Git status 실패를 깨끗함으로 보지 않는다
  - 기존/미merge 브랜치는 보존한다
  - UI 확인과 CLI 결과 반환을 구별한다
- 상태: 대상 앱 미실행.

<a id="ac-w05"></a>
## AC-W05 · 완료 worktree 일괄 정리

- 준비: OPEN/MERGED/CLOSED PR, merged branch, no-commit, dirty, pinned 사례
- 행동: Clean 후보 보기와 CLI clean 비교
- 기대 결과:
  - OPEN은 제외한다
  - MERGED 또는 자기 commit이 merge된 안전 후보만 기본 선택한다
  - closed-unmerged/no-commit은 기본 미선택이다
  - dirty/busy/pinned/status 오류는 보류한다
  - 성공과 남은 이유를 함께 보고한다
- 상태: 대상 앱 미실행.

## AC-B06 · Sleep과 깨우기

- 준비: 한 checkout에 Claude/Codex 세션과 일반 셸

<a id="ac-a04"></a>
## AC-A04 · Seen과 수동 확인

- 준비: fixtures/states.json의 고정 now와 done/idle/working
- 행동: 확인 처리, 기간 경과, seen off, working 전환
- 기대 결과:
  - 기본 120분간 Seen이다
  - 기간이 지나면 Idle이다
  - working이면 Seen이 아니다
  - seen off면 보존하지 않는다
  - 확인 처리가 프로세스 종료/메시지 전송을 하지 않는다

- 행동: runtime 변경 이벤트; 복구 선택과 auto 선호 조합
- 기대 결과:
  - 같은 runtime이면 재실행하지 않는다
  - 중복/다른 프로그램 대상은 제외한다
  - working만 continue 기본 선택이며 Codex 서버가 살아 있거나 확인 실패면 해제한다
  - 기록된 옵션/cwd로 이어간다
  - 사라진 공간은 임의 복구하지 않는다
  - 영속 저장 실패를 성공으로 간주하지 않는다
  - 저장 실패를 다음 주기에 재시도하며 복원 안내를 중복하지 않는다
  - 시작 직후(20초 미만) 런타임에서는 판단·기록하지 않아 이전 기록을 덮어쓰지 않는다
  - 살아 있지 않거나 다른 프로그램이 된 PID의 foreground·세션 파일을 실행 중으로 세지 않는다
  - 이전 run 기록을 보존하고 `hm restore`가 아직 실행되지 않는 세션을 다시 묻는다
- 상태: 대상 앱 미실행.

## AC-C03 · 지나간 UI 오류 기록

- 준비: 가상 상태 응답: 정상 → interrupted 반복 → 조회 실패 → 오류 유지 → 정상
- 행동: 오류 감시·기록 읽기·로그 회전을 실행한다
- 기대 결과:
  - 오류 스택과 발생 시각이 파일에 남는다
  - 동일 오류는 매초 중복 기록하지 않는다
  - 조회 실패를 복구로 기록하지 않는다
  - 회복 후 같은 오류가 다시 나면 새 발생으로 남긴다
  - 파일 용량과 보존 개수가 제한된다
  - 대화·제목·실행 인자 전체를 상태 자료로 복사하지 않는다
  - 폴링 사이의 짧은 오류 누락 가능성을 명시한다
  - 렌더 구간 합계·최대와 25ms 이상 완료를 기록하되 계측이 redraw를 만들지 않는다
  - 렌더 중 I/O 없이 메모리 집계하고 저장 실패 시 한 묶음을 재시도한다
  - 미완료 후 60초가 지나도 그 대기를 렌더 시간으로 기록하지 않는다
  - 느린 표본 개수·로그 용량을 제한하고 미저장 표본의 VM 폐기 시 유실을 명시한다
- 상태: 대상 앱 미실행. 현재 Herdr 진단기의 회귀 테스트와 대상 앱 합격은 구별한다.

## 이전 자체의 합격 기준

- 원본 shared/세션/worktree를 바꾸지 않고 사용자 메타데이터 사본을 만든다. 원본·대상 필드 수와 값을 비교한다.
- 경로 매핑은 prefix 경계를 지키고 다대일 충돌을 거부한다. missing 경로와 미지원 옵션은 보고서에 남긴다.
- 가져온 상태만으로 setup/agent resume/삭제가 실행되지 않는다. 실행 전환은 별도 단계다.
- 새 호스트 ID를 생성하고 원래 core/terminal/request ID를 재사용하지 않는다.
- 두 번 import해도 사용자 메모를 중복 생성하지 않는 idempotency 정책을 정한다. 현재 importer가 존재한다는 뜻은 아니다.
- 문제 발생 시 새 앱의 import만 되돌리고 source 사본으로 복귀할 수 있다.

## 이번 작성에서 확인한 범위

- 기존 WHY/코드와 기능·데이터·명령 대응을 정적 대조했다.
- 가상 예제는 형식과 문서 연결을 검사한다. 앱별 합격 사례는 아직 실행하지 않았다.
- 이전 작업에서 한도 Python 테스트 5개, Herdr 초기 check, 480/720px 실제 화면 확인을 수행했지만 전체 기능의 이식 완료 증거는 아니다.
- 원본 코드 없이 별도 재구현하는 검증(앞서 제안한 5단계)은 이번 요청 범위에 포함하지 않았다.
