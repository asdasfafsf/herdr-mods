# 렌더 성능을 하나씩 개선하기

목표는 작업이 많거나 컴퓨터가 바쁠 때도 목록이 중단되지 않고, 최신 이름·상태를 계속 확인하는 것이다. 오류 위치만 보고 그 함수가 유일한 원인이라고 단정하지 않는다. 한 렌더의 누적 작업량을 줄이고 같은 조건으로 비교한다.

## 반복 절차

1. 발생 화면·스택·시각·코드 버전과 데이터 규모를 `hm logs`에서 확인한다. 누락 가능성이 있는 상태 폴링임을 감안한다.
   `hm logs --render`의 구간 합계·최악 표본·미완료 마지막 구간도 함께 본다. 완료된 JS 설명 생성 시간과 호스트 전체 프레임 시간은 구별한다.
2. 사용자 데이터와 별개인 fixture로 호스트 조회 횟수와 표시 결과를 측정한다. 시간이 긴 후보 하나를 정한다.
3. 불필요한 반복을 줄이고, 표시·순서·공유 상태 쓰기가 이전과 같은지 비교한다. 다음 렌더에서 수정한 데이터가 반영되는지도 확인한다.
4. Herdr의 실제 엔진으로 같은 fixture를 검사하고, 설치 뒤 실제 화면과 여러 갱신 주기의 오류를 확인한다. Node 모의 시간과 native 실행 시간을 섞지 않는다.
5. 결과와 아직 남은 후보를 기록하고 커밋한다. 다음 후보도 먼저 측정한 뒤 수정한다.

## 2026-11-09: agents-plus의 반복 목록 조회

비교 기준: `dced0ef`. Herdr 0.1.13에서 별도 지연 렌더는 30/40ms를 통과하고 60/80ms에서 `interrupted`로 중단됐다. 이는 실행 시간 제한이 같은 오류를 낼 수 있다는 재현이며, 사용자가 처음 본 오류의 당시 실행 시간을 측정한 것은 아니다.

40개 내부 에이전트 + 14개 외부 에이전트 fixture의 초기 렌더에서:

| 호스트에서 읽는 자료 | 수정 전 | 수정 후 |
|---|---:|---:|
| 전체 pane 목록 | 80회 | 1회 |
| 전체 워크트리 목록 | 94회 | 1회 |
| 외부 행의 메타데이터 | 14회 | 1회 |

pane 목록을 매번 복사하던 `lead(tab)`에 한 번 읽은 목록을 전달한다. 탭 제목과 space별 레포 정보를 렌더 안에서 계산해 재사용하고, 외부 행용 checkout 경로는 한 번만 정렬한다. 다음 렌더까지 데이터를 저장하는 캐시는 아니므로 이름·경로·제목 변경을 놓치지 않는다.

동일 fixture와 실제 GPUI 빌더를 사용하는 임시 mod의 `herdr-app check`에서 얻은 단일 실행 관측:

| 규모 | 수정 전 | 수정 후 |
|---|---:|---:|
| 내부 40 + 외부 14 | 25ms | 3ms |
| 내부 200 + 외부 67 | interrupted | 27ms |

위 수치는 **가상 호스트 데이터를 이용한 native 초기 렌더**이며 사용자 화면의 모든 상호작용 지연을 측정한 것은 아니다. mock 호스트의 자료 복사 구현도 실제 Herdr의 Rust→JS 경계와 같지 않다. Node 비교에서는 Priority/Grouped/접힌 사이드바/대규모 화면의 요소 설명과 명령·공유 쓰기 결과가 이전과 같음을 확인했다. 코드·환경이 바뀌면 다시 측정한다.

```sh
node --experimental-vm-modules tests/agents-render.mjs
node --experimental-vm-modules tests/agents-render.mjs --before dced0ef --native
```

`--native`는 임시 폴더의 가상 mod만 검사하고 제거한다. 실제 앱의 레이아웃·상태·세션을 바꾸지 않는다. native 수정본의 오류는 검사 실패로 처리하며, 기준 코드의 interrupted는 비교 결과로 보고한다.

## 2026-11-09: Seen·옵션·레포 색의 반복 조회

비교 기준: `6dda1fb`. 같은 40개 내부 + 14개 외부 fixture의 초기 렌더에서:

| 호스트에서 읽는 자료 | 수정 전 | 수정 후 |
|---|---:|---:|
| 보기 옵션 | 200회 | 1회 |
| 읽음 상태(ack) | 92회 | 1회 |
| 레포 색 / 공간 색 | 각각 40회 | 각각 1회 |

같은 native 초기 렌더의 단일 관측은 40개에서 4→3ms, 200개에서 30→20ms였다. Node 모의 40개 측정은 오히려 느려진 실행도 있었으므로 모든 환경에서 같은 속도 향상을 보장하지 않는다. 확정적인 개선은 행 수만큼 늘던 호스트 읽기를 일정하게 줄인 것이다.

옵션은 한 렌더 동안 함께 쓰지만, 다음 렌더와 클릭/비동기 작업은 새 값을 읽는다. 작업을 다시 시작한 에이전트의 ack를 정리한 결과도 그 렌더에 반영한다. `option`, `seenFor`, `shownStatus`, `repoTag`의 기존 호출 방식은 유지하며, 명시적으로 스냅샷을 넘기는 호출만 이를 재사용한다.

비교 검사는 Seen 끄기·기간 변경·구버전 옵션 별칭·색 변경·모두 읽음 클릭·작업 재개 후 ack 제거를 추가했다. 표시 결과와 클릭이 공유하는 값이 이전 코드와 같은지 확인한다.

```sh
node --experimental-vm-modules tests/agents-render.mjs --before 6dda1fb --native
```

## 다음 측정 후보

- 다른 mod는 오류 빈도와 측정 결과가 있는 순서로 다룬다. 이번 수정만으로 전체 UI 시간 초과가 해결됐다고 판정하지 않는다.
- 매우 큰 목록은 데이터 탐색 외에 요소 생성 비용도 커진다. 가시 영역만 그리는 방식이 필요한지는 더 큰 fixture와 실제 사용 규모를 보고 판단한다.

## 2026-11-09: 하위 에이전트 탐색

비교 기준: `413ca92`. 내부 에이전트 120개 중 24개에 5단계 자식(총 터미널 240개)이 있는 fixture를 추가했다. 이전에는 자식을 방문할 때마다 전체 터미널을 filter하고, 긴급도와 화면에서 같은 트리를 두 번 탐색했다.

부모별 live 터미널 인덱스를 한 번 만들고 각 에이전트의 자손 목록을 렌더 안에서 재사용한다. 원래 깊이 우선 순서·연결선·자식의 긴급도 반영은 유지한다.

- 초기 렌더의 전체 터미널 filter 검사: **115,440개 항목 → 240개 항목**. 남은 filter는 pin 이전 처리이며, 새 부모 인덱스를 위한 별도 한 번의 240개 순회가 있다. 이 수치는 전체 연산 횟수가 아니라 반복 전체 배열 filter의 비용이다.
- native 단일 관측: 200개/1단계 fixture **20→17ms**, 120개/5단계 fixture **17→13ms**. 40개는 양쪽 모두 3ms였다.
- 종료된 자식 제외, 부모 변경, 새 자식 추가 후에도 기준 코드와 같은 요소 설명을 만드는지 비교했다. 접힌 사이드바에서도 긴급도 계산을 유지한다.

```sh
node --experimental-vm-modules tests/agents-render.mjs --before 413ca92 --native
```
