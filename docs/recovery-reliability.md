# 실패를 성공으로 기록하지 않기

시작 후 복구 지연의 실측은 [2026-11-15 시작 지연 감사](restore-startup-latency.md)에 있다.
20초 안정화 대기, 실제 세션 식별 비용, 명령 전달 후 준비 시간의 측정 한계를 구분한다.

2026-11-10 개선. 복원 기록을 저장하지 못했는데 메모리에서 완료로 처리하면 재부팅 전에 복구할 기회를 잃는다. 한도 조회나 mod 설치도 실패를 성공으로 표시하면 사용자가 오래된 값·코드를 믿게 된다. 각 기능은 **실제 완료를 확인한 뒤 성공 상태로 전환**해야 한다.

| 기능 | 완료 조건 | 실패 시 동작 |
|---|---|---|
| 복원 기록 | `writeTextFile`의 원자적 비교·교체 성공 | 기존 저장 캐시 유지, 다음 5초 주기에 재시도. 초기 읽기 실패는 파일 부재로 취급하지 않음 |
| 복원 안내·자동 이어가기 | 같은 인스턴스에서 런타임 변경을 처리 | 기록 저장 실패 때문에 같은 안내/요청을 반복하지 않음 |
| 복원 판단 | 런타임이 20초 이상 돌았고, foreground PID가 지금 그 에이전트를 실행 | 그 전에는 판단·기록하지 않음. 직전 run 기록은 `previous.json`에 남겨 `hm restore`로 다시 물음 |
| 세션 식별 | agent PID와 세션 ID를 연결 | 터미널 조회 실패·foreground 부재·ID 미식별을 구분해 주소와 함께 기록. 이름 대조 실패의 정확한 원인은 별도 확인 |
| 한도 Refresh | 두 서비스의 직접 조회가 모두 성공 | 일부 성공은 Partial, 모두 실패/잘못된 helper 응답은 Failed. 기존 값과 시각 유지, hover에 이유 |
| mod 설치 | 임시 파일 검사 및 교체 후 검사 성공 | 기존 파일 백업, 교체 실패 시 해당 mod 복구. 실패·건너뜀은 exit 1, 설정·명령 갱신 중단 |

2026-11-14 재부팅에서 복구 창이 뜨지 않고 기록이 덮어써졌다. 앱이 core보다 먼저 떠서, core가 터미널을 재부팅 전 상태(claude foreground, 옛 PID)로 보고하던 약 2초 사이에 첫 판단을 했다. 모든 세션이 실행 중으로 보여 안내 없이 끝났고, 다음 확인에서 기록을 덮어썼다. 판단 지연·PID 확인·이전 run 보존을 더했다. 그 시점의 core 응답은 남아 있지 않아 타이밍은 프로세스 시작 시각(앱 12:00:39, core 12:00:43, 터미널 프로그램 재시작 12:00:45)과 코드 경로로 추정했다.

복원 진단은 `hm logs --restore`로 읽는다. 안내 때마다 `offer`(기록 수·안내 수·제외 사유와 터미널 주소)를 남긴다. 기록 위치·보존량·한계는 [UI 진단](ui-diagnostics.md), 이식 합격 조건은 [acceptance](porting/acceptance.md)에 있다. 설치는 mod별 복구이며 먼저 성공한 다른 mod까지 되돌리는 번들 트랜잭션은 아니다. 검사도 초기 view 검사이므로 이후 비동기 오류를 모두 잡지는 못한다.

## 검증

```sh
python3 -m unittest discover -s tests -p 'test_*.py'
node tests/failure-recovery.mjs
node --experimental-vm-modules tests/session-parity.mjs
python3 scripts/check-porting-docs.py
./install.sh restore usage commands
hm logs --restore
herdr-app status
```

- Python 34개 검사: 기존 기능과 설치 사전/사후 검사 실패, 부분 복사 실패 복구, 첫 설치 실패 정리, 빈 오류 출력/검사 timeout, 진단 회전·CLI 읽기, 직접 조회 실패/잠금 경합을 포함한다.
- JS 실패 주입: 시작 20초 미만 런타임에서 안내·기록 없음, 이전 run 보존, 연속 저장 실패 뒤 성공, 초기 읽기 실패와 재시도 읽기 실패, LIVE 갱신, 복원 안내/자동 이어가기 중복 방지, 한도 helper 비정상 종료·깨진 응답·부분 성공·회복·중복 요청 방지를 확인했다.
- 실제 첫 설치에서 검사 timeout이 발생해 이전 복원 mod로 되돌아가고 exit 1인 것을 확인했다. 기존 코드 검사 및 재시도 설치는 통과했다. 최초 검사 지연의 원인은 확정하지 않았다.
- 최종 설치 전·후 native 검사 통과, 앱 오류 목록 없음, 실제 화면 확인. 실제 한도 직접 조회는 Claude·Codex 모두 성공했고 명시적인 결과 필드를 반환했다.
- 기존 작업을 종료하지 않았다. 실제 코어 재시작 후 복원은 아직 별도 검증이 필요하다. 공유 Codex 서버의 제목/cwd 식별 한계도 [기능 대조](codex-parity.md)에 남아 있다.
